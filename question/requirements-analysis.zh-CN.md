# Take-home assignment 需求解读

> 本文是基于 6 张题目图片的初步分析，属于实现建议，不是原题新增要求。完整英文转录见 [assignment.md](assignment.md)。目前尚未验证 ClinicalTrials.gov 在线 API 的实际接口、字段和限制，也尚未开始编码。

## 1. 这次要交付什么

实现一个 AI 辅助的后端服务：接收临床试验相关的自然语言问题，理解查询意图，从 ClinicalTrials.gov API 获取数据，并返回前端可以直接据此绘图的结构化结果。

预期流程可以拆成：

1. 自然语言问题和可选筛选字段。
2. 经过校验的查询与分析计划。
3. ClinicalTrials.gov 数据获取。
4. 数据清洗、去重、分组和统计。
5. 图表类型选择与可视化规格生成。
6. 返回数据、展示映射、元信息，以及可选的数据来源引用。

题目预计投入约 24 小时；允许任意语言、库、AI 工具和互联网资源。这里的 24 小时是题目给出的工作量预期，图片没有给出明确提交截止日期。

## 2. 必须完成、设计目标和加分项

| 分类 | 内容 | 解读 |
| --- | --- | --- |
| 必须 | 接收字符串 `query` | 其他结构化输入由候选人自定，不必照抄示例字段 |
| 必须 | 使用 ClinicalTrials.gov Data API | 图表数值要来自实际数据获取与计算 |
| 必须 | 返回结构化可视化输出 | 包括 `type`、`title`、`encoding`、`data`，以及渲染所需元信息 |
| 必须 | 写清请求和响应 schema | 字段、类型、必填性、校验，以及图表数据的含义需要明确 |
| 设计目标 | 统一方案覆盖多类问题和多种图表 | 题目强调扩展性，避免为每个示例单独硬编码 |
| 必须 | 提交可运行源码和 README | README 要包括运行方法、schema、设计取舍、局限和后续改进 |
| 必须 | 提供 3–5 个真实运行案例 | 每个案例包含查询和系统实际产生的 JSON；不能把题目示例当真实结果 |
| 必须 | README 说明 AI 工具使用和正确性验证 | 解释自主设计与生成后修改的部分 |
| 必须 | 最终打包为 zip | 包含上述交付物 |
| 加分 | Deep citations | 图表中的每个数据点能够追溯到相关试验及 API 原文字段或值 |
| 可选 | UI、部署地址、演示视频 | 不应挤占核心后端与数据正确性的时间 |

注意：第 1 节提到判断是否需要可视化，但第 4 节明确要求答案通过可视化规格表达。实现成功路径应以结构化图表为主要输出；无数据、意图不明确或不支持的请求应另行定义清晰行为。

## 3. 评分重点

| 评分项 | 权重 | 实现时应提供的证据 |
| --- | --- | --- |
| 系统设计 | 35% | 模块边界清晰；方案可扩展；对真实 API 数据有合理处理 |
| AI / Agent 设计 | 20% | 受约束的计划、明确工具边界、输入与输出验证、避免幻觉 |
| 代码质量 | 20% | 可读性、组织、文档、正确性和鲁棒性 |
| 查询与可视化覆盖 | 15% | 多类问题、多种图表，并通过通用逻辑实现 |
| 输入输出设计 | 10% | 无歧义的 schema；前端能够可靠渲染 |

系统设计和 AI / Agent 设计合计 55%。因此建议先建立可靠的“理解问题 → 获取数据 → 确定性计算 → 生成图表规格”链路，再拓展覆盖面。网络图与来源追溯有价值，但需要清楚定义统计含义。

## 4. 建议的实现边界

### 模型负责语义规划，程序负责数据与计算

建议让模型生成受 schema 约束的分析计划，例如查询实体、筛选条件、分析类型、分组维度、时间粒度和图表偏好。服务端验证计划之后，再调用固定工具获取数据并执行统计。

图表数值、试验 ID 和引用内容应从 API 返回的数据中确定性生成。不要让模型凭文本直接编造统计结果，也不需要依赖模型输出自由形式的内部推理来证明系统正确。

### 先覆盖几类可复用分析

以下是建议范围，不是题目要求逐项实现的清单：

| 分析能力 | 示例 | 图表 |
| --- | --- | --- |
| 分类计数 | 按阶段、干预类型、国家统计 | 柱状图 |
| 时间分桶 | 按试验开始年份统计 | 时间序列 |
| 多组对比 | 两种药物的阶段分布 | 分组柱状图 |
| 实体关系聚合 | 某疾病试验中的申办方与药物关系 | 网络图 |

这些能力可共用筛选、数据规范化、去重、聚合和引用机制。散点图、直方图等可以在核心链路稳定后再考虑。

### 把统计口径写进元信息

需要尽早决定并记录：

- “某年试验数”具体使用哪个日期，是开始时间、注册时间还是其他时间。
- 一个试验包含多个阶段时，按组合阶段分组还是分别计入多个阶段。
- 一个试验出现在多个国家、包含多个药物时，如何计数，是否允许跨类别重复。
- 药物或申办方名称如何规范化，是否合并别名。
- 空值、未知阶段、缺失日期如何处理。
- 分页是否取完；如果结果受到数量或时间上限限制，如何标记数据不完整。
- 网络图的边代表“出现在同一试验”还是更强的关系。药物同现不能自动解释为两药联合用药，应依据实际试验字段确定能支持的表述。

这些属于建议处理的数据问题；具体 API 表达方式仍需后续查阅官方文档与实际响应。

### 来源追溯应贯穿计算过程

如果实现加分项，建议从规范化记录开始保留 `nct_id` 和字段证据。聚合时同步累计贡献记录，而不是最后再补一段来源文字。

对于“某阶段有 41 项试验”这样的统计，引用应能说明哪些试验贡献了这个计数。题目里的单条引用只是说明格式；实际实现需要明确是否完整列出贡献记录，或是否存在引用截断。

## 5. 建议实施顺序

1. 查阅官方 API 文档并验证少量真实响应：确认搜索、字段、分页及数据缺失情况。
2. 定义请求、分析计划、图表响应和错误响应的 schema。
3. 跑通一个端到端案例：问题理解、真实数据获取、统计、图表 JSON。
4. 抽出通用的规范化、分组、去重与证据追踪，再扩展其他图表。
5. 校验关键边界：无结果、缺失字段、多值字段、分页不完整、外部请求失败，以及无效模型计划。
6. 生成 3–5 个真实案例，检查计算和引用，完善 README，打包交付。
7. 有余力再增加 UI 或其他展示。

## 6. 后续研究需确认的事项

- 当前 ClinicalTrials.gov API 的具体搜索语法、可选字段、分页方式及访问限制。
- 药物、疾病、阶段、日期、申办方和地点等字段在真实响应中的结构与缺失情况。
- 技术栈和模型接入方案，以及在缺少模型凭证时采用怎样的明确行为。
- 题目未指定的 HTTP 路径、图表规范格式、错误协议和结构化筛选字段优先级。

这些属于后续实现选择或技术验证项，不应写成已经确定的原题要求。
